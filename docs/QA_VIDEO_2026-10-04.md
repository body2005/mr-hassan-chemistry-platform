## فرز الثغرات، بدون suppression

الموافقة البشرية الصريحة على مشاركة بيانات الصور/SBOM مع Docker Scout سبقت الفحص.
Scout 1.24.0، والنسختان Debian 13 Trixie. `ldd /usr/bin/ffmpeg` أثبت ربط librsvg،
libcjson، libxml2، libexpat؛ وجود الربط ليس إثبات exploit، ولا إثبات انعدام الوصول.

`apt-get update` و`apt-cache policy` على حاوية فحص مؤقتة من صورة المعالج الحالية
انتهيا Exit 0؛ لا تحديث داخل filesystem الإنتاج read-only. المصادر الفعلية:
`trixie`, `trixie-updates`, `trixie-security` من Debian؛ لا sid/forky.
كل نسخة أدناه هي candidate المفعّل أيضًا، وOpenSSL **3.5.7-1~deb13u3** مثبت.

## ما لم يُنجز بعد

أداة الاستعادة الموسعة فشلت أولًا قبلS3backup لأن`compose run --no-build`
خيار غير مدعوم. صُحّح الأمر إلى`run --pull never` دون`--build`، مع pin إلى
ID صورةAPI الفعلية عبرQAoverride؛ لا بناء من checkout المتغير. أعادfinally
الخدمات الأصلية بنجاح في المحاولة الفاشلة، وبقيت البيانات/volumes والـDBdump.
السجل `video-storage-20261004t121004z-7cba6e22.json` محفوظ؛
لا تُحسب تلك المحاولة نجاحrestore. نتيجة إعادة التشغيل تُسجل في جدول البوابات.

المستخدم أكد أثناء هذه الجولة أن freebuff يُعامل كأنه ما زال يعدّل Extract.
**لا تعديل لملفات Extract الآن ولا إعادة اختبار fidelity نهائي له**؛ تُعاد الصور
والبوابات النهائية بعد تأكيد انتهاء عمله. مطابقة source hashes الحالية لا تثبت
اكتمال Extract ولا تشمل تعديلًا يحدث بعد أخذ صورة Docker الحالية.

آخر فحص `verify-runtime-source.ps1` بعدrestore الساعة12:21UTC:72ملفًا داخلAPI
و72داخلvideo-worker،0mismatch في كل منهما، Exit0. `document_parsers.py` بقي
SHA-256 `C5FD0743B64CC1DAEEFD17508839A745D84D5806EDD982E5DC5CD654C7E7DAEC`؛
لم أكتب فيه. كل الخدماتالعشر healthy، ومنافذPG/Redis/S3 لاhost mapping؛
HTTPS والupload وMailpit على127.0.0.1 فقط. حفظrestore volumes بعد إيقافها.

### حادث سجلات QA، لا إخفاق وظيفي يُخفى

مجموعة integration كاملة على984c سجلت27/3/0، Exit1 (603.243s): اثنان فقدا
الدليل التشغيلي من السجلات، والثالث وجد total cgroup1613205504byte مقابل
memory.max1610612736byte. تكرار اختبارات السجلات فشل أيضًا؛ زيادة انتظار
السجل وجمع stream لم يُصلحا السبب، ولم تُعدّ النتيجة نجاحًا.

فحص ملف Docker json-file الفعلي للحاوية أثبت سجل JSON تالفًا عند offset86339
يحوي136null byte. API all/tail5000 كان يتوقف بعد65535byte، بينماtail100
يقرأ الأحداث الجديدة. فُحصت الخدمات العشر المعزولة؛ عُثر على تلف مماثل في
S3 (1241null byte) وproxy (161null byte). قُرئت الملفات دون تغييرها، وحُفظت
نسخ كاملة + SHA-256 + offsets في `.qa/audit2/log-evidence/` (لا رفع للـlogs).
أعيد إنشاء API/S3/proxy المتأثرة فقط، بنفس الصور وبقاء كلvolumes. بقية الخدمات
ومشروعchemistryprodlocal لم تُمس. لا ادعاء أن تبديلAPIversion أو انتظارlogs
عالج التلف. السبب المباشر مثبت؛ ربطه بانقطاع Docker Desktop استنتاج زمني،
وليس تحليلًا مثبتًا لسبب تلف Docker نفسه.

الأدوات المحفوظة: `infra/qa/inspect-log-file.py`,
`scripts/qa/repair-qa-log-corruption.ps1` (QAaudit2 فقط)، وprobeقراءةالسجل.
اختبار redaction ما زال يتطلب سجلًا موجبًا ويتحقق أن التوكن لا يظهر، لا نجاحًا
بسبب ملف فارغ. `operational_logs` يجمع finite stream، follow=False، ويفشل إذا
لم يظهر الدليل المطلوب.

بالنسبة للذاكرة، [توثيق kernel memory.max](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)
يسمح بتجاوز لحظي في بعض الظروف. اختبار QA يحفظ peak الحقيقي/cache/anon/
working set، ويتطلب العودة لنفس cap خلال15s وعدم زيادةoom/oom_kill/restarts،
مع بقاء حد anonymous512MiB دون زيادة. هذا تعديل فرضية القياس لا رفع حد
الحاوية؛ أي إخفاق في هذه الشروط يظل إخفاقًا. إعادة المجموعة بعد التعديلات
انتهت30/0/0، Exit0؛ اختبارات السجلات تطلب دليلًا موجبًا ولم تُستثنَ.

الـintegration الحالية أثبتت وصول طلبي Quiz submit فعليين متزامنين إلى
PostgreSQL: الردان 200 والدرجة5، وصف واحد فقط في QuizAttemptAnswer، بلا500.
الأعطال أحادية الخدمة: PG/Redis/S3→503، web→504، proxy→connection error،
Celery→قراءة200 (لا تعتمد عليه)، SMTP→طلب reset200 عام بلا تسريب وجود الحساب.
تعافت الخدمات السبع، وقائمة مقررات المدرس لم تتغير. هذه ليست اختبارات تعطل
video-worker/upload-gateway أثناء processing.

اختبارات الحدود أعادت نقل1GiB و5GiB ورفض+1byte؛ 5GiB هنا WebM padded
لا محاضرة واقعية بهذا الحجم. API total cgroup اقترب من1.5GiB ووصل إليه بسبب
file cache؛ في إعادة11:44 كان raw peak عند5GiB+1 =1,610,645,504byte،
مقابلcap1,610,612,736byte ثم عاد تحته، وanonymous peak355,622,912byte،
وworking set أقل من الحد؛ memory.events max ارتفع (ضغط/reclaim)، دون oom
أو restart. هذه ليست دلالة على هامش ذاكرة مريح تحت تزامن عالٍ.

Scout: التشغيل المتزامن الثاني تعطل بقفل cache (Exit1) دون SARIF جديد؛ أُعيد
منفردًا وأنتج SARIF worker النهائي مع9High/Exit2 للفحص نفسه (wrapper1). ظهر تحذير Windows
بعدم حذف archive مؤقت بسبب file-in-use؛ لم تُحذف مسارات عامة ولم تُخفَ الثغرات.

- DRM حقيقي يتطلب packager/CPIX/EME/license secrets وحسابًا وموافقة على التكلفة؛
  لا يحل بمجرد وضع license URL. لا خدمات خارجية أو شراء من تلقاء نفسي.
- HLS الحالي غير مشفر: جلسة مصرح لها يمكنها حفظ المقاطع؛ لا ضمان «منع التحميل
  من Network/Download Manager 100%». حتى DRM لا يمنع تصوير الشاشة/الكاميرا.
- تحقق 4K/الهواتف/Safari/الصوت/ساعات من الفيديو وتعدد المعالجات وقت crash لم يكتمل.
- استجابة503 المفردة أثناءRecovery لا تزال غير مفسرة؛ لا حذف للفشل، ولا
  retry تلقائي يخفيه، ولا ادعاء أن الإعادتين الناجحتين تثبتان إصلاح سببه.
- snapshot متسق يحتاج وقف **API + Celery + video-worker + upload gateway**؛
  أُثبت الآن تشغيل المجموعة علىPG+S3 جديدين، لكن لا hot backup أو off-site
  encrypted backup أو RPO/RTO سيرفر خارجي. حفظ5أصول جاهزة هو sampling؛
  مطابقة snapshot462كائنًا و51جدولًا كاملة، وليست sampling.
- S3 object snapshot لا يستعيد أجزاء MPU غير المكتملة. أُصلح/اختُبر NoSuchUpload
  بعد إعادة البناء: حالة expired وإعادة اختيار الملف لإنشاء جلسة جديدة؛ لا استرجاع
  للأجزاء المفقودة ولا ادعاء استئنافها دون إعادة نقلها.
- legacy uploads ومرحلة إعادة التشغيل وإعداد الإنتاج الأساسي لم تُبدّل تلقائيًا؛
  overlay الحالي قابل للمراجعة/QA، وليس إذن نشر.
