# تجهيز RLS — غير مفعّل وغير معتمد بالتشغيل

هذه مرحلة تجهيز وليست حماية تعمل في PostgreSQL الآن. لا توجد Alembic migration
تفعّل RLS في المصدر المراجع. لم نتصل بقاعدة الإنتاج لقراءة pg_roles/pg_policies؛
حالة السياسات الحية وملكية الجداول وsuperuser/BYPASSRLS **غير معلومة**.
فلاتر SQLAlchemy وقيود المدرس/المؤسسة الموجودة هي صلاحيات تطبيق، وليست RLS.

## الملفات المجهزة

- `infra/rls-status.sql.example`: قراءة metadata فقط، دون أسرار أو بيانات طلاب.
  يبيّن المالك، عضوية دور المالك، RLS/FORCE وخصائص دور الاتصال والسياسات.
- `infra/rls-review.sql.example`: مسودة سياسات tenant للجداول ذات institution_id
  وسياسات عبر الأب لجداول الوحدات والدروس والتسجيلات وروابط التقييم والإجابات.
  `USING` يقيّد SELECT/UPDATE/DELETE، و`WITH CHECK` يقيّد INSERT/UPDATE.
  السياسة restrictive تمنع سياسة permissive إضافية من توسيع حدود المؤسسة.
  **لا يحتوي الملف ENABLE أو FORCE أو grants أو إنشاء أدوار**، وليس في startup.
  مسودة tenant لا تفصل مدرسين أو طلابًا داخل المؤسسة؛ يستمر فرض ذلك في التطبيق.
- `app/core/rls_context.py`: هوية immutable من مستخدم تحقق الخادم من نشاطه ودوره
  وإبطال جلسته وعائلتها. متوقف افتراضيًا بـ`RLS_CONTEXT_ENABLED=false`.
  لا يثق بـheaders أو هوية داخل payload. `set_config(..., true)` مرتبط بالمعاملة
  وينتهي بالـcommit/rollback؛ after_begin يعيد الهوية بعد commit داخل الطلب نفسه.
  `get_db` ينظف Session.info عند انتهاء الطلب، مع rollback/close بواسطة Session.
  bind متصل بمساري CurrentUser وOptionalUser فقط حاليًا.

## شروط تمنع التفعيل حاليًا

1. أنشئ لاحقًا دور runtime منفصلًا غير مالك، NOSUPERUSER/NOBYPASSRLS، ولا يكون
   عضوًا في دور المالك. دور migration مختلف خارج التطبيق. لا تمنح BYPASSRLS.
   فحص المسودة يرفض الأدوار غير المناسبة لكنه لا ينشئها ولا يمنحها شيئًا.
2. المصادقة تحتاج قراءة users/refresh_sessions قبل هوية الطلب. هذه الجداول مستثناة
   من المسودة؛ يلزم فصل اتصال المصادقة بدور محدود/واجهات SQL محددة قبل توسيع RLS
   لها، مع صلاحيات لا تسمح لتطبيق الطلبات بتعداد بيانات الدخول.
3. الزائر يحتاج catalog منشورًا؛ لا تعطه هوية مؤسسة من query أو header. جهّز
   دور catalog مستقلًا وسياسة SELECT للحقول العامة فقط أو واجهة محددة الإسقاط.
   لا تمنح الزائر وصولًا للملفات أو الإجابات أو الدرجات أو الطلبات المالية.
4. مسارات الفيديو تعتمد على token مع cookie حية، وبعض preview يعتمد على سياق
   مختلف؛ يجب ربط سياق DB بعد تحققها بالكامل أيضًا قبل تفعيل سياسات lessons/assets.
5. معالج الكمبيوتر يكتشف VideoUpload من طابور PostgreSQL عالمي. يلزم dispatcher
   بدور محدود بقراءة/claim job IDs، ثم session جديدة لكل job تتحقق من owner/lesson/
   course وتربط المؤسسة الموثوقة. كذلك maintenance والإشعارات وحذف التخزين لها
   جلسات غير مرتبطة بطلب HTTP. لا تستخدم مؤسسة اعتباطية ولا وصولًا عامًا كحل.
6. video_uploads وstorage_cleanup وجداول هوية/إيصال الإشعارات ونسخ الأسئلة تحتاج
   سياسات إضافية ونموذج ملكية متوافق. المسودة ليست تغطية كل جدول.
7. PLATFORM_ADMIN لديه استثناءات وصول عالمي صريحة في بعض خدمات الدورات/المحتوى.
   المسودة تقيده بالمؤسسة الحالية. يلزم حسم هذا العقد بدور إدارة منفصل، لا استثناء
   شامل أو BYPASSRLS للتطبيق. لا تدّع أن ذلك متوافق تلقائيًا الآن.
8. اختبر لاحقًا، بإذن جديد، عدم وصول مؤسسة لأخرى، CRUD، الأدوار داخل المؤسسة،
   login/refresh/public catalog، background jobs، rollback/pool reuse وفقد السياق.
   لم تنفذ هذه الرحلات أو SQL في هذه الجولة.

بعد استيفاء الشروط والنسخة الاحتياطية، راجع سياسة كل جدول في staging ثم ENABLE
وFORCE تدريجيًا في نشر مستقل. لا تشغّل المسودة على الإنتاج الآن، ولا تضفها إلى
`alembic upgrade head`. عودة إصدارات التطبيق دون سياق موثوق بعد التفعيل ستكسر
الوصول؛ جهّز rollback للأدوار والسياسات قبل التفعيل، مع إبقاء صلاحيات التطبيق.
